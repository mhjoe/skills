# Docu-Git 버전 관리 & 요약 추출 지침서 (Versioning & Summary Protocol)

이 지침서는 **Docu-Git** 스킬이 문서를 생성, 저장, 수정할 때 적용하는 버전 번호 부여 규칙, 파일 명명 규칙, 그리고 커밋 로그 요약 추출 가이드라인을 정의합니다.

---

## 1. 문서 버전 관리 규칙 (Document Semantic Versioning)

버전 번호는 **이력에서 기계적으로 계산**합니다. 에이전트가 문서의 완성도나 진행 단계를 짐작해 번호를 고르지 않습니다.
(문서가 얼마나 완성되었는지는 저자만 판단할 수 있고, 그 판단은 §1.2의 사용자 확인으로만 번호에 반영됩니다.)

### 1.1 번호 부여 절차 (필수 — 이 순서로만 번호를 정한다)
1. **이력 확인**: 프로젝트의 `DOCU_HISTORY.md`(또는 매니페스트 JSON)에서 해당 문서(`doc_id`)의 직전 커밋 버전을 찾는다.
2. **이력이 없으면 `v0.1`.** 이미 완성도 높은 원고라도 예외 없다.
   - 이미 존재하던 파일은 번호를 소급 부여하지 않고, 처음 관리하는 시점의 파일을 **`v0.1` 기준본(baseline)** 으로 등록한다. 기존 파일명은 사용자가 요청하지 않는 한 바꾸지 않는다.
   - 기준본 이후의 첫 작업물은 `v0.2`이다.
3. **이력이 있으면 직전 버전 + 0.1** (`v0.3` → `v0.4`). 한 번의 작업에서 편집 단위가 여럿이면 단위마다 +0.1.
4. 번호는 **문서(`doc_id`) 단위로 독립**이다. 같은 프로젝트의 원고와 검토 보고서는 각자 `v0.1`에서 시작한다. 프로젝트 전체를 대표하는 단일 번호는 두지 않는다.
5. 모든 커밋에 **`버전 근거`** 를 한 줄로 적는다. 허용되는 근거는 세 가지뿐이다.
   - `이력 없음 → v0.1`
   - `직전 v0.X + 0.1`
   - `사용자 지정 (v0.X, {지정/확인한 시점})`
6. **활동 기록(`act-`)은 번호를 소모하지 않는다.** 문서·산출물 파일이 바뀌지 않은 사전준비·자료조사·분석·검토·의사결정은 `activities[]`에 따로 기록하고, 문서 버전은 그대로 둔다. 번호가 오르는 것은 문서 내용이 실제로 바뀌는 문서 커밋뿐이다. 활동 기록은 `관련 문서`에 그 시점의 문서 버전을 **참조만** 한다. (`activity_logging.md` §2)
   - 활동 중에 산출 파일을 새로 만들거나 고쳤다면 그 파일에 대한 문서 커밋이 생기며, 이때만 §1.1-3으로 +0.1 한다.
   - 문서가 아직 없는 프로젝트에서 활동만 쌓여도, 첫 문서는 `v0.1`에서 시작한다(활동 수와 무관).

### 1.2 사용자 확인이 필요한 경우 (확인 없이 부여 금지)
다음 번호는 §1.1로 계산되는 번호가 아니므로, **반드시 사용자에게 먼저 묻고** 답을 받은 뒤 부여한다.
- `v0.5`, `v1.0`, `v2.0` 같은 **이정표 번호**, 또는 직전 +0.1이 아닌 모든 번호(번호 점프)
- 이력이 없는데 파일명에 이미 버전 표기가 있는 경우(기존 표기를 인정할지)
- 이력과 실제 파일 상태가 맞지 않아 직전 버전을 확정할 수 없는 경우

에이전트는 이정표가 적절해 보이면 **제안만** 한다. 예: "개요·본문·결론이 갖춰져 v0.5로 올리는 것을 제안합니다. 올릴까요, 직전 번호+0.1로 둘까요?"

### 1.3 버전 의미 가이드 (해석용 — 시작 번호나 선택지가 아님)
사용자가 번호를 지정했거나 확인한 뒤, 그 번호가 어떤 단계를 뜻하는지 설명할 때만 참고한다.
- **Major (`X`)**: `v1.0` 최초 완전한 완성본(확정본·제출본·발행본) / `v2.0` 전면 개작, 목차 구조 전면 재구성, 연구 방향의 근본적 전환
- **Minor (`Y`)**: `v0.1` 최초 기준본 또는 개요·초안 / `v0.2~v0.4` 내용 작성·보완 / `v0.5` 이론적 뼈대 통합 등 주요 업데이트 / `v0.6~v0.9` 서론·본론·결론 보완, 문장 정교화, 참고문헌 정제 / `v1.1`, `v1.2` … 확정본 이후의 부분 수정·지적사항 반영

### 1.4 금지 사례
- "서론~결론이 갖춰져 있어 `v0.9`" — 완성도 추정으로 번호를 고른 것 (§1.1 위반)
- "참고문헌 정제 단계이므로 `v0.8`" — §1.3을 시작 번호로 읽은 것
- "이전 버전 번호는 소급하지 않는다"고 쓰면서 이력 없는 문서에 `v0.9`를 부여 — 서술과 행동의 모순
- 사용자에게 묻지 않고 `v1.0`·`v0.5`로 올리는 것
- **번호는 직전 최신본(`v0.6`) + 0.1로 매기면서 편집은 옛 파일(`v0.2`)에 한 것** — 번호만 보면 최신본이지만 `v0.3`~`v0.6`의 수정(그림 교체·수치 정정·조판)이 모두 사라진다 (§1.6 위반, 실제 발생 사례)

### 1.5 번호 정정 절차
사용자가 번호에 이의를 제기하거나 잘못 부여된 것을 발견하면:
1. 어떤 기준으로 그 번호를 붙였는지 **그대로 설명**하고 잘못이 있으면 인정한다.
2. §1.1로 다시 계산한 정정 번호를 제시하고 적용한다. 파일명을 바꾸고, 같은 문서의 이후 버전도 연쇄 정정한다.
3. `DOCU_HISTORY.md`에 정정 사실(이전 표기 → 정정 표기, 사유)을 남기고 매니페스트의 `history[]`에 `corrected_from`을 기록한다. 이력을 지우지 않는다.

### 1.6 편집 기준본(Base) 규칙 — 번호와 원본 파일은 반드시 짝이 맞아야 한다
§1.1은 **번호**를 정할 뿐, **어느 파일을 열어 고칠지**는 정하지 않는다. 번호는 `v0.6 + 0.1`인데 실제로는 `v0.2` 파일을 열어 고치면, 새 파일은 최신본처럼 보이지만 그 사이 버전의 수정이 모두 사라진다. 이를 막기 위해 다음을 지킨다.

1. **기본 기준본 = 직전 최신본.** 문서 커밋의 편집 원본은 항상 해당 `doc_id`의 `current_file`(직전 버전 파일)이다. 번호가 `직전 v0.X + 0.1`이면 원본도 반드시 `v0.X` 파일이어야 한다.
2. **"v0.X 기준"이라는 말은 원본 지정이 아니다.** "v0.2 검증 결과 반영", "v0.2에서 지적된 오탈자", "0.2 원고 기준으로" 같은 표현은 **무엇을 고칠지의 출처**를 말할 뿐이다. 그 내용을 최신본에 반영한다. 원본 지정인지 모호하면 작업 전에 묻는다. 예: "v0.2에서 지적된 내용을 최신본 v0.6에 반영할까요, v0.2 파일 자체를 고칠까요? 후자는 v0.3~v0.6의 수정(…)이 빠집니다."
3. **최신이 아닌 파일에서 출발해야 할 때(사용자가 명시적으로 원할 때)만** 다음 순서를 따른다.
   - 기준본과 최신본 사이의 커밋 요약(`v0.X+1`~최신)을 보여 주고, **사라지는 수정 목록**을 명시해 확인을 받는다.
   - 확인을 받으면 `docu-git rollback` 또는 `docu-git branch`로 처리한다. 작업 유형은 `ROLLBACK`/`BRANCH`, 파일명 요약에 `(v0.X기준)`을, 커밋의 `편집 기준본`에 실제 원본을 적는다.
   - 사라진 수정을 다시 반영할지도 함께 묻는다.
4. **착수 전 중복 점검.** 요청된 수정이 최신본에 **이미 반영되어 있는지** 먼저 확인한다(검색·대조). 모두 반영되어 있으면 새 버전을 만들지 않고 "이미 v0.X에서 반영됨(해당 커밋)"이라고 보고한다. 필요하면 활동 기록(`REVIEW`)만 남긴다. 일부만 남았으면 남은 것만 고친다.
5. **저장 후 회귀 점검(필수).** 새 파일을 직전 버전 파일과 비교해, **의도한 변경 외의 차이가 없음**을 확인한다.
   - 비교 항목: 본문 텍스트(문단 단위 diff), 삽입 이미지(바이너리 해시), 쪽수, 표 개수.
   - 의도하지 않은 차이가 있으면 저장본을 확정하지 않는다. 원인(잘못된 기준본, 도구 부작용 등)을 확인해 다시 작업하거나 사용자에게 보고한다.
   - 결과를 커밋의 `회귀 점검` 필드에 한 줄로 남긴다. 예: `직전 v0.6 대비: 텍스트 6곳(의도) 외 차이 없음, 이미지 9/9 동일, 35쪽 유지`
6. **이력에 기준본 기록.** 모든 문서 커밋에 `편집 기준본`(파일명과 버전)을 적고, 매니페스트 `history[]`에 `base_version`·`base_file`·`regression_check`를 기록한다. `base_version`이 `previous_version`과 다르면 작업 유형이 `ROLLBACK`/`BRANCH`이고 사용자 확인 기록이 있어야 한다. 아니면 규칙 위반이다.

## 2. 파일 명명 규칙 (Filename Conventions)

로컬 디렉토리에 저장되는 모든 문서 파일은 다음 명명 형식을 엄격히 따릅니다.

### 2.1 저장 포맷
```text
{문서 기본명}_v{버전}_{주요 변경 요약}.{확장자}
```

### 2.2 작성 규칙
1. **문서 기본명**: 띄어쓰기 허용, 문서의 핵심 주제 또는 프로젝트명 (예: `행정정책분야 성과관리 논문`)
2. **버전**: `v0.1`, `v0.5`, `v1.0` 등 소문자 `v` 접두사
3. **주요 변경 요약**: 해당 버전의 핵심 변경 사항을 괄호 또는 명료한 단어로 표현 (15자 이내 권장)
4. **확장자**: `.md`, `.hwpx`, `.docx`, `.txt` 등 사용자가 지정하거나 기본 설정된 포맷

### 2.3 저장 예시
> 아래 번호(`v0.5`, `v0.8`, `v1.0` 등)는 **파일명 형식을 보여 주는 예시**일 뿐, 시작 번호나 추천 번호가 아닙니다. 실제 번호는 §1.1 절차로만 정합니다.

- `성과관리논문_v0.1_기본개요 및 목차구성.md`
- `성과관리논문_v0.5_이론 단일화(젠의 역량접근법).md`
- `성과관리논문_v0.8_실증분석 결과 반영.hwpx`
- `성과관리논문_v1.0_최종확정본.md`

## 3. 고밀도 요약 및 핵심 추출 지침 (High-Density Summary Protocol)

Docu-Git은 원문의 길이와 관계없이 이력에 기록되는 로그를 **핵심 요지를 손실하지 않는 고밀도 요약** 형식으로 유지해야 합니다.

### 3.1 요약 원칙
1. **노이즈 제거**: 수사적 표현, 인사말, 반복 설명 제거
2. **핵심 전달**:
   - **User Input 요약**: 사용자의 핵심 Intent(의도), 요청 변경사항, 추가/삭제 지시 사항
   - **Output 산출물 요약**: 생성/수정된 핵심 결론, 변경된 논리 구조, 새로 반영된 이론/데이터
3. **길이 제한**: 입력 및 출력 각각 3~5 줄 이내 (부렛 포인트 활용)

### 3.2 요약 표준 구조
```markdown
- **요청 의도**: [사용자가 요청한 핵심 변경/생성 목적 1문장]
- **주요 수정/추가 내용**:
  - [핵심 변경점 1]
  - [핵심 변경점 2]
- **산출물 핵심 요지**: [최종 결과물의 주요 결론 또는 구조적 변화 1~2문장]
```
